FieldNote — the product, specified.

FieldNote watches the AI-deployment talks so a decision-maker doesn't have to. It converts firsthand YouTube and X accounts of real enterprise AI deployments into short, verified, decision-ready records — and delivers them to the right person for near-zero cost of their own attention or tokens.

The two constraints that shape every decision here

1 · Firsthand only — a record exists only if a named person from a named company describes their own deployment in their own public words. 2 · The user is token-capped — the product spends the tokens once, centrally, so the buyer consumes verified answers for almost none of their own.

01 · Problem & value proposition

The buyer is drowning in AI noise and paying to stay confused.

New models and "agentic AI" launches arrive weekly at peak hype. An enterprise decision-maker who wants the one thing that matters — what a company like mine actually deployed, and whether it worked — has only bad options: sift hundreds of hours of talks themselves, or ask an LLM and burn their limited token budget on an answer they then have to fact-check (94% of B2B buyers already do).

FieldNote's value: the expensive, unreliable research is done once, centrally, and verified. The buyer gets a short, sourced, decision-ready record — cheap and trustworthy, against a status quo that is costly and unreliable.

Product promise

Discover what other enterprises actually did with AI · Understand the problem, models, architecture, challenges, deployment and ROI · Decide what applies to you — without spending your own tokens or trust.

03 · The ingestion workflow

A source-first cascade — cost rises only as confidence rises.

The pipeline is deliberately inverted from "search everything, then filter." It starts from a curated registry of high-yield sources and spends expensive tokens only on the small share of videos that survive cheap gates. Volumes below are illustrative of the funnel shape, per month.

04 · Modules & functional requirements

Nine modules. What each must do.

M1

Source Registry

The curated whitelist that seeds discovery and keeps signal high.

M2

Discovery

Pulls new candidate videos on metadata alone — no transcripts, no LLM.

M3

Cheap Gate

Free captions + small model classify firsthand relevance and field coverage.

M4

Extraction

Capable model structures survivors into the record schema, grounded in quotes.

M5

SCRUB / Review

Human confirms every claim, grades evidence, approves for publish.

M6

Entity & Library

Dedupes into company/deployment entities; the versioned record store.

M7

Search & Filter

Token-free discovery over structured records by role, workflow, grade.

M8

Profile & Fit

Role-based profile; maps records to "why this matters to you."

M9

Freshness

Dating, decay flags and a re-review cadence so records don't rot.

M1 · Source Registry

  • Maintain a curated registry of sources: YouTube channels, playlists, conference tracks, podcasts, and X handles, each tagged with expected yield and domain. MUST
  • Support source tiers: Tier A whitelist (crawled fully) and Tier B keyword search (crawled sparingly, quota-budgeted).
  • Admin can add / disable / re-tier a source and see its historical hit-rate (published records ÷ videos ingested).

M2 · Discovery (metadata only)

  • Pull new videos from Tier-A sources via the YouTube Data API on a schedule; record video ID, title, description, channel, duration, publish date, view count. MUST
  • Filter on metadata only — drop shorts, off-topic, and out-of-window items before any transcript or model call. MUST
  • Budget the API quota — prefer playlist/channel listing over search (100 units each); alert before the daily 10,000-unit cap.
  • Deduplicate against already-seen video IDs; never re-ingest.

M3 · Cheap Gate

  • Retrieve existing captions (creator or auto) via the transcript API — free — before any paid transcription. Fall back to Whisper only when captions are disabled. MUST
  • Classify with a small / cheap model: is this a firsthand, named-company enterprise deployment? Output Y/N, company, speaker+role, which schema fields are present, and a confidence score. MUST
  • Only items above a confidence threshold pass to Extraction; the rest are archived with the reason.
  • Cache the caption and gate result by video ID.

M4 · Extraction

  • Populate the record schema (§05) with a capable model from the transcript. MUST
  • Ground every populated field with a verbatim quote and a source timestamp. No field may contain a claim without a supporting quote. MUST
  • Fields not evidenced in the source are set to not_disclosed — never inferred or filled from outside knowledge. MUST
  • Normalize outcome metrics to a controlled vocabulary (deflection / resolution / containment / CSAT / handle-time / cost) and flag whether a baseline was stated.
  • Use prompt caching for the fixed schema + instructions to cut per-record cost.

M5 · SCRUB / Review

  • Present each extracted record beside its source so a human can confirm each quote and timestamp against the video. MUST
  • Assign an evidence grade (A–D, §06) per outcome claim and an overall record grade. MUST
  • No record reaches published without passing SCRUB. MUST
  • Capture right-of-reply status and reviewer identity + date.

M6 · Entity & Library

  • Resolve to company / deployment entities — multiple videos about one deployment merge into one entity with several sources, not duplicate records. MUST
  • Store records with full version history; every edit is versioned and dated.
  • Tag each record against the taxonomy (industry · workflow · technology · deployment stage).

M7 · Search & Filter

  • Browse, search and filter records by workflow, industry, company size, technology, evidence grade and outcome type — over structured fields, using none of the user's tokens. MUST
  • Results show the TL;DR layer only, with grade and freshness, so scanning is instant.

M8 · Profile & Fit

  • Minimal role-based profile — role, industry, company size, workflows of interest, goals. No account onboarding call. MUST
  • Surface a personalized feed and, per record, a "why this matters to you" fit note derived from the profile.
  • Any generative fit assistance runs server-side on FieldNote's tokens, cached and capped per account — never metered against the user. MUST

M9 · Freshness

  • Every record shows source date and last-reviewed date.
  • Flag records past a decay window (e.g. models/pricing likely stale) for re-review; surface freshness in the UI.
05 · The deployment-record schema

One record = one company's firsthand deployment.

This is the product's atomic unit and its output contract. Every field is either evidenced (quote + timestamp) or explicitly not_disclosed.

Hard rule

No number, model name, or architecture detail may appear in a record without a supporting verbatim quote and timestamp. A field with no source is not_disclosed, shown as such. This rule is the moat — the moment the product fabricates to look complete, it becomes the untrustworthy thing it replaces.

06 · Evidence grading

Every outcome carries how much to trust it.

GradeMeansTypical firsthand signal
AIndependent-quality production evidence with a baselineOperator states before/after with a named metric and time window
BNamed first-party disclosure with numbers, baseline partialExec gives a figure but not a clean baseline / control
CDirectional claim, no baseline / single-source"It's been a huge win" with no measure
DAnnouncement / aspirational / later walked backLaunch hype, projected numbers, conflicting statements

Metric hygiene is enforced at grading: deflection ≠ resolution ≠ containment ≠ handle-rate. A record that conflates them is graded down until the metric type is pinned to a quote.

07 · The consumption model

Progressive disclosure — respect the user's tokens and attention.

A token-capped buyer will not read a transcript. Records are delivered in three layers; the user drills only when a record earns it. The core loop is generative-token-free for the user.

LAYER 1

TL;DR

One line: what they did, whether it worked, evidence grade, freshness. Enough to triage in a scan.

LAYER 2

Decision card

Structured: problem · models · architecture · deployment · challenges · ROI · boundaries · fit-to-you.

LAYER 3

Evidence

On demand: the verbatim quotes, timestamps and source links behind every field.

The three-verb loop

01

Discover

By role/workflow — a personalized feed of relevant records, token-free.

02

Examine

A sourced, graded record with the lesson and the boundaries visible.

03

Apply

The "why this matters to you" fit note turns a record into a decision input.

08 · Token economics

Two separate budgets. Don't confuse them.

EconomyWhose budgetDesign response
ProcessingFieldNote (cost of goods)Source-first cascade · free captions · cheap-gate-then-capable-model · cache by video ID · prompt caching · per-record token budget + monthly cap
ConsumptionThe user (the binding constraint)Pre-computed records · search/filter over structure (no generation on read) · any AI fit-assist runs server-side on FieldNote tokens, cached & capped · never a metered chat box
The positioning this buys

"We spent the tokens so you don't have to." A fixed, predictable subscription that returns verified answers — versus the buyer burning a capped, unpredictable budget on answers they can't trust anyway.

09 · Non-functional requirements

The qualities that make it trustworthy.

  • Trust / accuracy — zero unsourced claims in published records; 100% of published records have passed human SCRUB.
  • Rights & compliance — short excerpts + attribution + link + timestamp only; never host or republish full media/transcripts; respect YouTube & X ToS and API quotas; obtain a standing IP opinion on the fair-use posture.
  • Privacy — minimal profile data; no personal data in URLs; standard auth.
  • Performance — search/filter and record views return fast from pre-computed data; no user-facing action blocks on an LLM call.
  • Freshness — records dated; decay-flagged; re-review cadence enforced.
  • Cost control — processing stays within per-record and monthly token caps; quota alerts before hard limits.
10 · Reference architecture

Serverless, batch-first, thin at the edge.

Heavy work is offline batch (protect margin); the user-facing app is a thin reader over pre-computed data (protect the user's tokens). Aligns with the FieldNote AWS reference architecture.

Ingestion
Scheduled jobs (Step Functions / EventBridge) → YouTube Data API + transcript retrieval → object store for raw captions.
Models
Small/cheap model for the gate; capable model (Claude via Bedrock) for extraction; prompt caching on the fixed schema.
Human-in-loop
Review queue (task-token pattern) for SCRUB; nothing publishes without it.
Data
Postgres (records, entities, taxonomy, versions) + pgvector for semantic search over structured records.
App
Thin web app: auth, profile, search/filter, tiered record views. No per-view generation.
Fit assist
Optional, server-side, cached, capped — retrieval-grounded over the library, on FieldNote's budget.

Concierge/validation phase can run on the lighter Netlify + Supabase stack; AWS is for the production/scale build.

11 · Metrics & go/no-go gates

How we know it's working — and when to stop.

Content-engine health

  • Yield — published records ÷ videos discovered (target: cascade keeps this economical).
  • Cost per published record — total processing tokens ÷ records (must sit inside the per-record budget).
  • Coverage — records per workflow; watch order-status (thin firsthand).

Product / demand

  • Repeat use · evidence used in a real decision · willingness to pay.
Validation gate (before building the automated pipeline)

Hand-produce ~20 records (21 candidates already in hand) and put them + a no-code role page in front of 10–15 CS leaders. Proceed only if, e.g., ≥5 repeat users, ≥2 say it changed a decision, ≥2 would pay. Miss → stop cheaply. Automate M1–M4 only after this passes.
